## Scope and result

T17 adds a thread-safe session store, a versioned per-session cache, a bounded synchronous task runner, and a hard final-result gate around the T16 Agent loop. The fixed upstream checkout remains unchanged. All provider failures are local fixtures; this task made zero remote requests and downloaded nothing.

Session state is keyed only by opaque `session_id`. Human-readable display names may collide and never select storage. Patch application and record replacement happen under one lock, so concurrent feedback cannot overwrite a newer snapshot. Cache keys contain `session_id`, `profile_version`, and request fingerprint; values are deep-copied on write and read, and writing a new profile version removes old entries for that session.

The Agent's final result now rechecks positive unique IDs, maximum K, explicit and seen exclusions, included/excluded genres, year bounds, and required title/genre/year metadata whenever a validated structured request is available. An invalid result may cause the single T16 replan, but it is never released to the caller.

| no feasible candidates | `NO_FEASIBLE_ITEMS` | 0 replans; constraints were not relaxed |
| excluded/wrong-genre/wrong-year item | `INVALID_RESULT` | one bounded replan, no response released |
| synchronous tool exceeds 20 ms | `TOOL_TIMEOUT` | caller returned under 0.5 second; no automatic retry |
| tool itself raises `TimeoutError` | `TOOL_EXCEPTION` | not misclassified as runner wait timeout |

All 429 and timeout transports declare `is_live=false`; their attempts are fixture accounting, not remote API requests.

## Session and cache isolation

- Two sessions with the same display name retained different user IDs and feedback.
- Concurrent feedback to two asynchronous sessions never crossed state.
- Thirty-two simultaneous patches to one session produced version 32 with all 32 event IDs and item updates present.
- Clearing one session did not mutate another session.
- Unknown sessions and duplicate session IDs fail closed.
- Cached mutable values cannot be changed through caller-owned or returned references.
- Feedback changes `profile_version`; the old cache entry cannot be read and is removed when the new version is stored.

## Why a synchronous task can keep consuming resources after timeout

A timeout on `Future.result()` stops the caller from waiting; it does not safely terminate Python code already running in another thread. `Future.cancel()` succeeds only before the worker starts. Once running, the function may continue using CPU, holding locks, waiting on I/O, or mutating external state until it returns. Force-killing a Python thread is unsafe because it can leave shared state inconsistent.

The new runner therefore uses a bounded pool, returns a structured `TOOL_TIMEOUT`, records whether work may continue, and marks timed-out tools non-retryable to avoid duplicate side effects. This bounds caller latency and concurrent worker count, but it is not hard cancellation. Untrusted or indefinitely blocking work needs a subprocess/process worker that can be terminated, or cooperative cancellation inside the tool. Service shutdown may also wait for a still-running thread when graceful cleanup is requested.
